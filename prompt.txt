Task 0 — Auto-update mechanism (do this first)

Why first: once this works, every future fix or feature (including the three below) can ship to whoever's running the app — you or the business owner — without manually rebuilding an installer and re-sending it.

Goal: the app checks for new versions on launch, downloads updates in the background, and prompts to restart and install. No GitHub credentials should ever be embedded in the shipped app — only used locally by the developer when publishing a new version.

Requirements:

Add electron-updater as a dependency.
Add a "publish" block to the build config in package.json pointing at the GitHub repo this project lives in (provider: github), so electron-builder knows where to check for and upload releases.
In main.js, after the app is ready, call autoUpdater.checkForUpdatesAndNotify() (or equivalent), and handle the update-downloaded event with a simple prompt ("Update ready — restart now?") rather than forcing a restart mid-use.
Confirm the update check fails silently and harmlessly if there's no internet connection — it should never block the app from opening normally.
Document the exact publish workflow going forward: bump "version" in package.json, then run the publish build command (e.g. electron-builder --publish always) with a GH_TOKEN environment variable set locally (repo-scope Personal Access Token) — never commit this token or bundle it into the app itself.
Confirm: since the repo is public, the installed app can check for and download releases with no authentication at all — only the publish step needs a token, and only on the developer's machine.
Task 1 — Bulk import/export (CSV/Excel)

Goal: let the admin import many products at once from a spreadsheet, and export the current catalog back out to one.

Requirements:

Add an "Import Products" action in the renderer UI that opens a file picker for .csv or .xlsx.
Map spreadsheet columns to the existing product fields in the Product model — reuse the existing model/validation logic rather than writing parallel insert code. Provide clear column-name requirements (e.g., a downloadable template) so the mapping isn't guesswork for the admin.
Before committing any rows, run every parsed row through the existing ValidationEngine and show a preview: how many rows will import cleanly, and a clear per-row list of what's wrong with any that won't (missing required field, duplicate product code, etc.) — don't partially import silently.
Add an "Export Products" action that writes the current catalog to .csv (and/or .xlsx), using the same field set, so it round-trips with the import format.
Handle images sensibly: since spreadsheet rows can't embed image files, decide and document the approach — e.g. an "image filename" column referencing files the admin has already placed in a designated import-images folder, which get copied/processed through the existing ImageProcessor pipeline during import.
Log the import result (rows added, rows skipped, errors) using the existing Activity model, consistent with how other actions are already logged.
Task 2 — Site search/filter for visitors

Goal: let a visitor on the live static site filter/search products by name, category, or tag — entirely client-side, no server.

Requirements:

Extend (or add alongside) the existing JsonGenerator.js output to produce a single JSON index of all published products at publish time — name, category, tags, thumbnail path, and the product page URL. Reuse this generator rather than building a second, parallel data-export path.
Add a lightweight vanilla-JS search/filter UI to the generated category pages (matching the existing site's styling, no new frameworks) that loads this JSON index and filters the visible product grid live as the visitor types or picks a category/tag.
Keep this genuinely static — no external search service, no API calls, no build step beyond what CategoryPageGenerator/JsonGenerator already do at publish time.
Make sure the JSON index is regenerated automatically every time the admin publishes, so it never goes stale relative to the actual catalog.
Confirm this degrades gracefully — if JS fails to load for any visitor, the existing static category pages still work exactly as they do today.
Task 3 — Product variants (size/color/fabric) — do this as its own dedicated round, not combined with Tasks 1–2

Goal: support multiple variants per product (e.g. different fabric or color options for the same saree design), each independently trackable for stock status.

Requirements:

Design a variants table linked to products (foreign key), with fields for variant type/label (e.g. "Fabric: Silk", "Color: Maroon") and its own stock status — don't try to force this into the existing products table directly.
Write a migration that is safe against the current production data: every one of the existing 16 products must end up with the correct default state after migration (e.g. treated as a single default variant), with zero data loss and no manual cleanup required afterward.
Update the admin UI: adding/editing a product needs a way to add, edit, and remove variants under it, each with its own stock toggle.
Update the in-stock/out-of-stock/auto-archive logic (currently per-product) to work per-variant — decide and clearly document how a product's overall displayed status is derived when it has a mix of in-stock and out-of-stock variants (e.g. "in stock" if any variant is available).
Update CategoryPageGenerator.js to render variant selectors on generated product pages, and to keep schema.org product markup and SEO fields accurate when a product has multiple variants (this is where a subtle SEO regression could sneak in — check it explicitly).
Update the WhatsApp inquiry link generation so the pre-filled message correctly references the specific variant the visitor was viewing, not just the base product name.
Run the full existing test/validation flow (ValidationEngine, publish, and a manual check of a couple of real products) after this change specifically, since it touches more of the codebase than Tasks 1–2 combined.
